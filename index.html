What's happening

The vulnerable mode simulates code like for (i = 0; i < len; i++) { if (guess[i] != secret[i]) return false; }, which stops comparing the moment it finds a mismatch. That means a guess that gets the first 3 characters right takes measurably longer to reject than one that gets 0 characters right — the comparison "walked further" before bailing out. An attacker who can measure response time doesn't need to guess the whole secret at once: they can brute-force it one position at a time, keeping whichever next character makes the timing go up, then moving to the next position. This turns an exponential guessing problem into a linear one.

The fixed mode simulates a constant-time comparison (e.g. XOR-and-accumulate across the full length regardless of mismatches, like MessageDigest.isEqual or hmac.compare_digest), which always does the same amount of work no matter how many characters are correct — so the timing bars stay flat and leak nothing.

Built for SE/CprE 4210 Learning Sprint #3, Problem 5. No real secrets, network requests, or timing measurements are involved — everything here is a simulated, local-only animation of the concept.
